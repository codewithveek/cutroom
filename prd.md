## 1. Summary

Cutroom reads a software project's codebase and produces finished product videos: launch videos, feature drops, tutorials, explainers, teasers and social cutdowns. The output is a 16:9, 9:16, 1:1 or 4:5 MP4 with voiceover, music, captions and a thumbnail.

An agent does the work a motion designer and a copywriter would do:
1. It reads the repository.
2. It writes a product brief with evidence.
3. It picks a video structure and a visual style.
4. It writes the script.
5. It **audits every claim against the code**.
6. It hands the user a storyboard to approve.
7. It renders the result.

The agent runs on **open-weight models**. Gemma does the reasoning and Kokoro does the voice, so in **Local mode** the whole pipeline runs on the user's laptop with no network access. Private code never leaves the machine, and each video costs nothing to produce.

## 2. Problem and users

**The problem.** Teams ship features weekly, but a decent launch video still costs $300–$3,000 from a freelancer, or two to five days of a developer's time in After Effects or Remotion. So most launches ship with a screenshot and a paragraph. General AI video tools don't help much:
- They can't read a codebase.
- They invent UI and features the product doesn't have.
- They require uploading private source code to a third party.

**Who uses it and who pays.**

| Persona | Job to be done | Why they pay |
|---|---|---|
| Indie hacker / solo founder | A launch video for Product Hunt, X and LinkedIn this week | Saves days; no motion-design skill needed |
| Dev-tool startup (2–20 people) | A video for every release, plus 9:16 cutdowns | Replaces a recurring freelancer cost |
| DevRel / docs team | Tutorials that stay true to the current UI | Videos regenerate when the code changes |
| Agency / consultancy | Client launch videos, under NDA | Local mode keeps client code on their own machine |

**Pricing hypothesis** (for the write-up's "who would pay" section):
- **Free tier:** self-hosted and Local mode, open source.
- **Hosted plan, ~$19/month:** cloud rendering on GPUs, ElevenLabs voices and team presets.
- **Agency plan:** per-seat licensing for client work.

## 3. Goals and non-goals

### Goals
- **G1:** Repo in, MP4 out: one command or one wizard produces a watchable 30–60 s video.
- **G2:** Every on-screen claim traces to evidence in the code (file and line), or is flagged.
- **G3:** Local mode runs end to end on open models with zero outbound network calls, and enforces this in code, not just in documentation.
- **G4:** Four visual styles, six presets and four aspect ratios, all from **one** storyboard.
- **G5:** A durable pipeline: a crashed render resumes from the last completed step.
- **G6:** A codebase a reviewer would call production-grade: typed contracts, modular packages, tests and tracing.

### Non-goals (this build)
- Multi-tenant accounts, billing and authentication. Single user only; auth is stubbed behind an interface.
- Rebuilding app screens as pixel-perfect React components. Cutroom uses captured screenshots plus code-derived blocks (§7.14).
- Free-form, LLM-written Remotion code. The model never writes TSX (see Principle P3).
- Video editing on a timeline. Users edit the storyboard, not frames.
- Live-action footage, avatars and lip-sync.

## 5. Product principles (invariants)

These are rules the code enforces, not aspirations.

- **P1 · Everything shown is real.** Motion is free; invention is not. Buttons, labels, statuses, numbers and behaviours shown in a video must exist in the code. Placeholder *data* (names, amounts) is fine. Placeholder *features* are not.
- **P2 · Narration drives timing.** Scene lengths are computed from synthesized voice durations. They are never hand-timed.
- **P3 · Models fill contracts; code renders.** The LLM outputs JSON validated against Zod schemas from `@cutroom/scene-spec`. A fixed, tested library of scene blocks renders it. The model never generates JSX.
- **P4 · Privacy is a mode, enforced at the provider boundary.** Each mode (Local, Hybrid, Cloud) has an allow-list of provider network scopes. A provider outside the allow-list throws `PrivacyViolationError` at construction time. In Hybrid mode, the approved storyboard JSON is the only thing that crosses to the cloud, and the user sees an egress manifest first.
- **P5 · One storyboard, every shape.** Aspect ratio is a render-time parameter. Blocks lay themselves out per ratio.
- **P6 · Deterministic renders.** The same storyboard, voice cache and seed produce the same MP4. Seeded randomness only.
- **P7 · Verify what you can't watch.** Every render produces stills at key frames and an audio loudness report. These are surfaced to the user.

## 6. User journeys

### 6.1 Web (primary)
1. **New video.** The user picks a source: a local folder path, a git URL, or an uploaded zip. They choose a privacy mode (Local, the default, or Cloud).
2. **Analysis (about 1–3 min).** A live pipeline timeline shows each step. The result is a **Product brief**:
   - Name, one-line pitch, audience and problem.
   - 3–6 features, each with evidence chips (`src/billing/payouts.ts:42`) that open a code viewer.
3. **Configure.** The user chooses:
   - **Video type**, with a recommended option.
   - **Look**: four cards, each with a live 3-second preview rendered by `@remotion/player`. One is recommended, with a one-line reason tied to *their* product.
   - **Aspect ratios** (multi-select).
   - **Target length.**
   - **Voice**: Kokoro voices, or ElevenLabs in Cloud mode.
   - **Music**: a generated bed, or an uploaded file.
   - **Brand**: accent colour, font and logo, auto-detected from the repo and editable.

   Presets fill all of these in one click.
4. **Storyboard review.** A scene list on the left and a preview on the right, with a ratio switcher.
   - Each scene card shows its block type, headline, narration, transition, estimated duration and a **claim audit badge** (Supported / Weak / Unsupported, with evidence or a suggested rewrite).
   - The user edits text inline, reorders scenes, swaps blocks, or regenerates one scene.
   - Unsupported claims block approval until they are fixed or explicitly overridden with a typed acknowledgment.
5. **Approve → render.** One progress row per ratio: voice, then render, then normalize, then thumbnail and captions.
6. **Deliver.** A player and downloads (MP4, `.vtt`, thumbnail JPG/PNG), plus a delivery note listing:
   - What is illustrative (data, hostnames).
   - The licences that apply (voice, music, Remotion).
   - What the user must still judge by eye and ear.

### 6.2 CLI (for Local mode, CI and the demo)
```bash
pnpm cutroom make --repo ./path/to/app --preset launch-editorial --ratios 16:9,9:16 --privacy local
pnpm cutroom make --repo . --preset launch-editorial --yes   # auto-approve (no human review)
```
The CLI uses the same pipeline and contracts as the web app. Without `--yes`, it prints the storyboard and claim audit and asks for approval in the terminal.

### 7.2 Privacy modes (`@cutroom/providers`)
Two axes are configured separately: **where the model runs** and **where rendering runs**. The storyboard JSON (`RenderJob`, §8.3) is the only contract between the two halves.

| Mode | Local machine | Cloud | Data that leaves the machine |
|---|---|---|---|
| **Local** | Ingest, Gemma (Ollama), Kokoro, render | — | Nothing |
| **Hybrid** (default for private repos) | Ingest, Gemma analysis, storyboard, claim audit, review, Kokoro voice (or ElevenLabs) | Render worker | Only the approved `RenderJob` bundle: storyboard JSON, voice clips, brand assets, screenshots |
| **Cloud** | — | Ingest, hosted Gemma (GPU, OpenAI-compatible), ElevenLabs, SerpApi, render | The repo (public git URL or upload) |

| ID | Requirement | Pri |
|---|---|---|
| FR-PRV-1 | Three modes as above. Mode is chosen per run and stored on the run record | P0 (Local, Hybrid) / P1 (Cloud) |
| FR-PRV-2 | Each provider declares `networkScope: "none" \| "localhost" \| "external"`. The provider factory checks it against the mode's allow-list and throws `PrivacyViolationError` at construction. In Hybrid mode, only the render-upload client may be `external`; ElevenLabs is allowed only if the user opts in (it receives narration text, never code) | P0 |
| FR-PRV-3 | **Egress manifest** (Hybrid): before upload, list every file in the `RenderJob` bundle with size and type, plus every code excerpt it contains; the user confirms. The manifest hash is stored on the run | P0 |
| FR-PRV-4 | The UI and delivery note show the mode badge ("Ran fully local" / "Rendered in cloud, code stayed local") and the providers used | P0 |
| FR-PRV-5 | Integration test: Local mode with outbound network blocked except localhost must succeed. In Hybrid, a test asserts the upload payload contains only manifest-listed files | P1 |
| FR-PRV-6 | The remote render API authenticates with a per-user API token (`Authorization: Bearer`); bundles are deleted from the cloud 24 h after the run completes | P0 (Hybrid) |

### 7.3 Product analysis (agent step `analyze-product`)

|---|---|---|

### 7.4 Video types and presets
Video types are **deterministic beat templates**: code, not prompts. The model fills the beats; it does not invent structure. (In Hybrid mode, everything in this section runs locally.)

| Type | Beats | Length | Default look |
|---|---|---|---|
| `launch` | problem (2–3 lines) → introducing → pitch (3 cards) → product moments (3–4) → close | 40–60 s | Editorial (Graphic if little UI) |
| `feature-drop` | "New: X" → old way (1 line) → 2–3 moments → where to find it | 20–40 s | Editorial |
| `tutorial` | title → steps (one action each) → end card with "Next:" | 45–75 s | Studio |
| `explainer` | stage rail → one idea per scene (diagram/code/meter) → recap | 45–60 s | Editorial |
| `teaser` | kinetic lines on beat → name → date/CTA | 10–20 s | Graphic |
| `dev-integration` | keys/setup → request code card → response → result | 40–50 s | Graphic |

**Presets (P0):** a preset is `{ videoType, look, ratios, targetSeconds, voice, music }`, defined as data in `packages/presets`. The six presets:
- `launch-editorial`
- `api-launch-graphic`
- `tutorial-studio`
- `teaser-cinematic`
- `explainer-editorial`
- `social-cutdown-vertical` (9:16, 15–30 s, captions burned in, opens on the hook)

**Look recommendation (P0):** a pure function `recommendLook(videoType, productSignals) → { look, reason, alternatives }`. It applies a rules table based on video type, UI density (from the UI string inventory), brand darkness and target channel. It is never an LLM call, so it is explainable and testable.

### 7.5 Looks (visual styles) (`@cutroom/video-kit/looks`)
Four looks, each a typed token set: ground, ink, accent, alarm colour, font family and weights, card shadow, default transition, crossfade frames, pace (seconds per scene) and suggested music.

| Look | Ground | Type | Default transition / crossfade | Pace | Sound |
|---|---|---|---|---|---|
| **Studio** | Near-black, soft glow from below, drifting faint grid; app in a floating window | Inter, 800 headlines, uppercase brand-colour eyebrow | Crossfade + soft whoosh / 12 | 5–8 s | Voice first, music ducked |
| **Editorial** | Warm paper `#efeee9` + vignette; UI on white cards with warm shadow | Plus Jakarta Sans, bold, tight tracking; numbers 200–260 px | Focus pull / 14; circle reveal for brand moments; panel grow for detail | 3–5 s | Music-led |
| **Graphic** | `#fafafa` with a fine square grid fading from the centre; one inverted black scene allowed | Inter Tight, medium, strongly negative tracking; slabs 150 px | Colour slab / 12; hard cut on beat; zoom through squares to close | 2–4 s | Music-led |
| **Cinematic** | Near-black, low glow, lots of empty space | Geist, semi-bold, 90–120 px, light on dark | Slow focus pull / 20 | 5–8 s | Calm bed or slow voice |

**Motion rules for every look** (enforced in block implementations):
- Hold the resolved state ≥ 0.5 s before a transition.
- Ease out into values; nothing stops abruptly.
- One coloured phrase per line: problem in the alarm colour, promise in the accent, never both.
- Text rises out of a mask word by word, about 3 frames apart.
- In muted-first looks, every claim stays readable ≥ 1.5 s.
- The look's accent is replaced by the product's brand accent when one is detected or set.

### 7.6 Aspect ratios
| Ratio | Size | Layout rules |
|---|---|---|
| 16:9 | 1920×1080 | Default layouts |
| 9:16 | 1080×1920 | Headlines larger and wrapped; windows become 4:5 panels; camera zoom ≥ 2×; key content above the bottom 20% safe area and away from the right edge; captions burned in at 14% from the bottom; open on the hook, not the logo |
| 1:1 | 1080×1080 | Stacked layouts; captions burned in |
| 4:5 | 1080×1350 | As 1:1, with more vertical room |

Implemented with Remotion's `calculateMetadata` (dimensions and duration from `inputProps`) and a `useFrameShape()` hook that blocks read to pick their layout. No text under ~28 px at 1080 width in vertical formats.

### 7.7 Scene block catalogue (`@cutroom/video-kit/blocks`)
Every block = a Zod props schema in `scene-spec` + a component + a layout per frame shape + `allowedLooks` + `durationRange` + a list of **claim fields** (props the audit must check).

| Block | Shows | Claim fields | Pri |
|---|---|---|---|
| `title-card` | Product mark + name + tagline; "Introducing" variant | name, tagline | P0 |
| `kinetic-headline` | 1–3 lines rising word by word; `*starred*` words take accent/alarm | each line | P0 |
| `big-number` | `RuleLabel` + `Odometer` rolling to a value + one line beneath; optional "limit" state turning alarm colour | value, label, line | P0 |
| `feature-cards` | 2–4 cards (icon, verb title, one line) dealt or popped in | each card | P0 |
| `code-card` | A **real excerpt** from the repo (path shown), syntax-highlighted with Shiki, typed or revealed by line; ligatures off | the excerpt must match the file byte-for-byte after redaction | P0 |
| `terminal` | Commands typed at 12–24 chars/s with real output (from README/scripts) | commands, output | P0 |
| `word-slot` | A list stepping through a slot, neighbours faded | each item | P0 |
| `end-card` | Verbs as beats → mark, name, tagline, CTA pill, URL | CTA, URL | P0 |
| `screenshot-window` | A captured screenshot in an app window; camera keys aim at **real element boxes** from capture; cursor clicks real elements | target element texts | P1 |
| `diagram-flow` | Stage rail + nodes + connector lines drawn in (explainers) | node labels | P1 |
| `meter` / `cell-grid` | Bars or cells filling to real values | values | P2 |
| `orbit-chips` | Integrations/providers around rings | chip labels | P2 |

**Transitions (P0):** `fade`, `focus`, `circle` (with origin), `panel`, `slab`, `zoom`, `push`, `cut`. All last `crossfade` frames, so timing maths stays uniform; `cut` swaps at the midpoint. Built on `@remotion/transitions`.

### 7.8 Storyboard generation (agent step `plan-storyboard`)
| ID | Requirement | Pri |
|---|---|---|
| FR-SB-1 | Input: brief + video type template + look + target length. Output: `Storyboard` (Zod) whose scenes are a **discriminated union of block types allowed by the chosen look** | P0 |

**Key decision: `PipelineRunner` interface.** Steps are plain, typed, idempotent functions (`activities`). `InProcessRunner` (used by the CLI and Week-2 path) and `TemporalRunner` (durable, used by the API) call the same functions. This keeps the Week-2 cut viable and makes the steps unit-testable without Temporal.

### 8.3 Core contracts (`@cutroom/scene-spec`), sketch
```ts
export const aspectRatioSchema = z.enum(["16:9", "9:16", "1:1", "4:5"]);
export const lookIdSchema = z.enum(["studio", "editorial", "graphic", "cinematic"]);
export const transitionSchema = z.enum(["fade", "focus", "circle", "panel", "slab", "zoom", "push", "cut"]);

export const evidenceSchema = z.object({
  filePath: z.string(),
  lineStart: z.number().int().positive(),
  lineEnd: z.number().int().positive(),
  excerpt: z.string().max(400),
});

export const narrationLineSchema = z.object({
  text: z.string().min(1),               // shown in captions
  say: z.string().optional(),            // respelt for TTS
  atFrame: z.number().int().nonnegative().optional(),
});

const sceneBase = {
  id: z.string(),                         // ULID
  transitionIn: transitionSchema.optional(), // defaults to look's transition
  transitionOrigin: z.tuple([z.number(), z.number()]).optional(),
  baseFrames: z.number().int().positive(),
  narration: z.array(narrationLineSchema).default([]),
};

export const bigNumberSceneSchema = z.object({
  ...sceneBase,
  block: z.literal("big-number"),
  props: z.object({
    label: z.string().max(40),
    value: z.number(),
    format: z.enum(["integer", "percent", "currency"]),
    line: z.string().max(60),            // *starred* phrase takes accent
    limitState: z.boolean().default(false),
  }),
});
// …one schema per block; then:
export const sceneSchema = z.discriminatedUnion("block", [/* all block schemas */]);

export const storyboardSchema = z.object({
  id: z.string(),
  videoType: videoTypeSchema,
  look: lookIdSchema,
  brand: brandSchema,
  scenes: z.array(sceneSchema).min(3).max(16),
});
```
```ts

export const renderJobSchema = z.object({
```

### 8.4 Pipeline (Temporal workflow `produceVideoWorkflow`)
| # | Activity | Retries / timeout | Output persisted |
|---|---|---|---|
| 1 | `ingestRepository` | 2 / 5 min | `RepoSnapshot` (storage) + summary row |
| 2 | `analyzeProduct` | 3, backoff / 10 min | `ProductBrief` |
| 3 | `planStoryboard` | 3 / 10 min (internal repair loop counts separately) | `storyboard_versions` v1 |
| 4 | `auditClaims` | 3 / 5 min | `claim_results` |
| — | **wait for signal** `approveStoryboard({ versionId, overrides })`; signal `updateStoryboard` re-runs step 4 for changed scenes | no timeout (status: `awaiting_review`) | — |
| 5 | `synthesizeVoice` | 3 / 10 min | voice clips + `VoiceTimeline` |
| 5b | `buildRenderJob` → in Hybrid: `confirmEgress` (signal) → `uploadRenderJob` | 3 / 10 min | `RenderJob` bundle + manifest hash |
| 6 | `renderRatio` × N (parallel, one per ratio); local worker, or remote worker consuming the uploaded `RenderJob` | 2, heartbeat every 10 s / 30 min | MP4 per ratio |
| 7 | `finalizeDeliverables` (loudness, VTT, thumbnail, cover art, delivery note) | 3 / 10 min | `assets` rows |
| 8 | `qualityCheck` (P1) | 2 / 5 min | stills + audio report |

- Activities are idempotent: each checks for its persisted output (keyed by run + step + input hash) before working.
- Each step emits `run_events`, which the API streams to the browser over SSE.
- Query `getRunStatus` serves the UI's polling fallback.

## 9. UI/UX design spec

**Design language:** dark-first, dense and precise, in the class of the Linear and Vercel dashboards. The app is a professional tool, not a toy; the *videos* carry the colour.
- **Stack:** Tailwind + shadcn/ui, themed via CSS variables. Geist Sans for the UI, Geist Mono for paths and code.
- **Colour:** a neutral greyscale with one accent (electric violet `#7c5cff`, tunable). Status colours: green = supported, amber = weak, red = unsupported/failed. A light theme is supported.
- **Layout:** a 56 px top bar (project switcher, privacy badge, command palette `⌘K`) and a three-pane workspace on the storyboard screen. Respect `prefers-reduced-motion` in the app UI.
- **Microcopy:** plain and specific ("3 claims need evidence", not "Oops!").

**Key screens**
1. **New video:** a stepper (Source → Privacy → Preset or custom → Brand). The privacy step explains Local mode in one sentence and shows the providers that will be used.
2. **Run timeline:** a vertical step list with live durations, token counts per model step, and expandable logs.
3. **Product brief:** feature cards with evidence chips. Clicking a chip opens a side sheet with the file excerpt and highlighted lines.
4. **Storyboard editor** (the hero screen):
   - **Left:** scene list (drag to reorder) with block icon, duration and audit badge.
   - **Centre:** `@remotion/player` preview with a ratio segmented control and a scrubber synced to the selected scene.
   - **Right:** an inspector with the block's props form (generated from its Zod schema), narration lines (text/say), transition, and audit details with "Apply suggestion".
   - **Footer:** "N unsupported claims" plus an Approve button (disabled until resolved or overridden).
5. **Renders:** one card per ratio with progress, ETA, then a player, downloads, quality stills strip, audio report and delivery note.
6. **Library:** a grid of past videos with thumbnail, look, ratio chips and date.

Accessibility: WCAG 2.1 AA contrast, full keyboard navigation of the editor, visible focus rings, and labels on all icon buttons.

## 10. Non-functional requirements

| Area | Target |
|---|---|
| Analysis time | ≤ 3 min for a repo of ≤ 2,000 tracked files on a 16 GB laptop with local Gemma (measure in evals; adjust model size) |
| Render time | ≤ 5 min per 60 s 1080p ratio on an 8-core CPU (measure; parallelise ratios within RAM limits) |
| Determinism | Same inputs → byte-stable storyboard rendering (seeded randomness) |
| Reliability | Killing the worker mid-render resumes from the last completed activity |
| Security | Secret redaction before any model call; read-only capture; no secrets in logs, traces or videos; path traversal blocked in the asset API and the ingest path |
| Licensing | Delivery note lists the licences: Remotion (free for individuals and companies ≤ 3 people; company licence above), Kokoro (Apache-2.0), ElevenLabs (commercial use on paid plans), generated music (no third party) |

**Code standards (mandatory)**
- TypeScript `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. **No `any`**; use `unknown` and narrow.
- Organise by domain/feature. No god functions or components: functions do one thing, components stay small.
- Descriptive names (`sceneDurationFrames`, never `d` or `f`).
- **Three or more parameters → an options object.**
- **kebab-case** file and folder names.
- Zod at every boundary: env, HTTP, model output, DB jsonb.
- Biome (or ESLint + Prettier) and `tsc --noEmit` in CI. Conventional commits.
- **Pin every Remotion package to one exact version** (`--save-exact`) and verify the CLI's render queue works after install; a past patch release shipped broken.
- Import `React` explicitly in every `.tsx` the Remotion bundler touches.
- Self-host fonts in `public/fonts` (via `@remotion/fonts`) so renders work behind proxies and offline.

## 11. Testing strategy
- **Unit (Vitest):** timing solver, word budget, recommend-look, redaction patterns, deterministic claim checks, schema narrowing, repair loop (with a fake model client).
- **Contract:** every block renders a still in every allowed look × every ratio from fixture props (`renderStill` snapshot hashes; review diffs).
- **Integration:** InProcessRunner end-to-end on the smallest fixture repo with a scripted fake model client. This is the CI-safe "repo in, MP4 out".
- **Privacy:** Local mode with network egress blocked (FR-PRV-4).
- **Evals:** real models, run manually (§7.17).

## 12. Deployment
- **Local:** `docker compose up` (Postgres+pgvector, Temporal dev server) + `ollama pull <gemma tag>` + `pnpm dev`.

  - Web and API on **Render**.

  - Gemma on a DigitalOcean GPU Droplet (OpenAI-compatible endpoint).
  - Temporal Cloud or a self-hosted Temporal.
  - Postgres on Tiger Data (P1).
